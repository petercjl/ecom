## 判断依据

`RenderFrameHostImpl::CouldDisplayBeforeUnloadDialog()` 的实现为 `has_before_unload_handler_ && HasStickyUserActivation()`，只证明注册了离开监听并获得过用户激活，不检查页面是否编辑、保存或是否会请求确认。使用这个条件独立阻止休眠，会把普通浏览交互当成未保存内容。

在修复前，原小红书页只做普通筛选交互，原生保护理由即出现 `BEFORE_UNLOAD`；没有表单／编辑保护理由。修复后对同一页面重复该非编辑交互，得到以下真实信号：

| 对象 | 可能离开确认 | 表单交互 | 用户编辑 | 结果 |
| --- | --- | --- | --- | --- |
| 原小红书搜索页 | true | false | false | 自动休眠成功 |
| 本地仅注册离开监听页 | true | false | false | 自动休眠成功 |
| 实际输入的 textarea，含离开监听 | true | true | true | 保持运行；手动休眠拒绝 |
| 实际输入的 contenteditable，无离开监听 | false | false | true | 保持运行；手动休眠拒绝 |
| 显式保持运行的任务页 | false | false | false | 保持运行；手动休眠拒绝 |

## 当前保护契约

离开监听作为只读诊断信息展示。实际休眠继续执行原生 PROACTIVE 资格检查，保留 `HadFormInteraction`、`HadUserEdits`（包括 contenteditable）、原生页面取数任务、显式保持运行、媒体、上传、设备、锁及其他既有保护；没有站点白名单、force 入口或任务绕过。

GUI 和 CLI 共用 `manualDiscard.editSignals`：检测可用状态、表单交互、用户编辑、可能离开确认及监听本身是否阻止休眠。检测不可用时编辑标志为 null，原生状态不可用仍阻止休眠。GUI 明确区分“已检测到编辑”和“未检测到编辑”，离开监听显示为提示。浏览器不试运行网站的离开处理器，以免触发其副作用。

内核编辑记录不是网站业务层的“已保存／未保存”接口：已编辑并保存的页面也可能继续受到保守保护，原生信号未覆盖的自定义编辑器、客服或外部页面任务使用明确的“保持运行”。当前规则减少监听导致的误判，同时保留编辑记录与任务保护。
