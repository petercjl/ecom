# P0 内存诊断验收与前后对照

日期：2026-11-06，Asia/Shanghai。平台：本机 macOS arm64、24 GiB、macOS 26.5.2。对应能力与边界见 [原生内存诊断](memory-diagnostics.md)，统计数据见 [对照 JSON](memory-p0-comparison-2026-11-06.json)。

## 结论

**P0 已完成原生快照、GUI 与 CLI 的共同接入，并通过实际 Dev 编译、重启和界面验证。本轮没有显示内存节省：重启约 7–8 分钟后的 footprint 中位数比重启前高 10.54%。** P0 只增加按需观测，没有开启 Memory Saver、执行休眠或更改自动回收策略；不能将这轮变化作为策略优化收益或证明新增诊断造成同等增量。

保持原有两个窗口、7 个标签、6 个账号容器，实例共 15 个进程，其中 9 个 renderer。当前窗口为账号管理、天猫商家中心、生意参谋与三个小红书页面；另有一个新标签页窗口。原先的单窗口观察与本次全窗口原生枚举分开记录。

- GUI：「账号管理 → 内存与标签页」，提供总量卡片、容器、标签、可展开进程表和手动刷新。中文／英文说明，明示估算、公共开销、不可用值与内核判定的业务边界。
- CLI：`memory status|tabs|containers|processes --json`，完整载荷共用 schema；兼容开发入口委托产品实现。
- npm 配套：canonical Skill、capabilities、帮助、README 与测试同步。本地开发候选沿用包版本 0.3.1，以具体内容哈希识别；没有发布或改变 npm 渠道。

原生功能提交为 `e20dbbb70`，Chromium 156 接口适配为 `35f5140af`。统一入口 `node ecom/build-dev.mjs` 最终构建并启动集成提交 **`5a1ace519a702e80458a442daf6f71ada38ebc97`**；该提交包含其他对话的 Windows 发布记录。运行主 PID 为 16990，固定 Dev 数据目录与原会话复用。

## 实际验收

1. **真实传输与计量**：新版声明 `memorySnapshotProtocol=1`；旧版在重启前返回 `BROWSER_UPGRADE_REQUIRED`。原生快照覆盖 7 个标签、默认会话加 6 个账号容器、15 个唯一进程。主 PID、实例 ID、容器映射、估算总量均通过校验。
2. **OS 交叉核对**：一次原生快照总量 2254.058647 MiB；随即在独立进程中对同一组 15 个 PID 调用 macOS `proc_pid_rusage`，总量与各进程值均一致，差值为 0。此项验证口径和传输，不代表跨时点值应始终一致。
3. **归因**：天猫与生意参谋映射到同一原有容器，三个小红书标签映射到另一容器；共享 renderer 只累计一次，再按已知关联页面估算分摊。各标签估算之和等于 `attributedBytes`，与未归因部分对账到实例总量。
4. **策略与原因**：运行管理器实际返回 `memorySaverActive=false`、state 0、aggressiveness 1、冻结偏好 true。可见页面返回可见／窗口选中等卸载限制，内置页返回 WebUI 冻结限制，后台页能区分 yes 与 varies；冻结及卸载原因分别呈现。
5. **GUI**：真实打开账号管理入口、内存页、进程明细并执行刷新；可访问性结构及屏幕目视均核对通过。页面数据非静态样例，刷新产生新时间与指标。界面测试后返回账号管理及原小红书标签。
6. **CLI 与 Skill**：产品包测试 41 项通过；开发入口与账号管理测试另有 13 项通过。新增用例覆盖唯一进程计量、未知指标、无效总量、重复 ID、未知关联、禁止写参数、真实私有信箱及旧版能力拒绝。包验证、Skill 格式／可移植性／能力合同检查、JS 语法检查通过；未进行 clean-context Agent 回归。
7. **真实打包与本机同步**：实际 npm pack 共 29 个文件，tarball SHA-256 为 `8e98a25923f74c375244a6f7eb1082ddb2ccd1fad5f20c1c04018bc683043f5f`。全局 `ecom-cli` 与本机 Codex 的独立 Skill runtime 已同步；关键源码、schema 与 runtime 哈希一致，文件 inode 独立，托管状态 `current=true`，已读取宿主目录中的新版 Skill。其他 Agent 的 Skill 与配置未同步。
8. **按需开销**：连续 20 次真实快照，OS 采样及汇总耗时中位数 **0.0905 ms**，完整 CLI 调用中位数 **131.64 ms**。这 20 次期间主进程 footprint 变化 **−0.046875 MiB**，未出现明显累积；短测不构成长期无泄漏或完整 CPU 开销证明。GUI 无后台自动轮询。

共享包审计的包内工作流扫描发现 CI／OIDC 等发布层提示；发布 workflow 位于仓库级且本轮不发布，这些结构性提示没有被当作功能运行失败，也没有据此宣称发布就绪。Windows GUI 分支仅有实现，Windows 原生采样、CLI 传输与 ACL 不在本轮已验证范围。

## 下一阶段

P0 已能回答哪个容器、标签及进程占用内存，以及内核为何保持页面运行。实际节省仍需 P1：统一业务保护、主动卸载、压力及预算调度，再在相近负载、相同活动页和稳定等待时点下复测。GPU 增量同时列为独立诊断方向，先取得资源归因证据，再决定回收措施。
