# Ecom 店铺容器 PRD

## 目标

在一个 Ecom 浏览器中管理多个电商平台、多个店铺账号。用户按店铺名称识别容器，使用现有原生容器标识区分标签并隔离网站会话。创建店铺容器包含平台选择和人工登录，登录与身份核验完成后进入可用状态。

该文档是产品需求与实施设计。macOS Dev 已具备原生容器和后台只读取数通路；平台目录、待配置流程、身份绑定及独立管理页的实现按下列合同验收。登录检查与具体店铺身份绑定分别验收；当前服务返回登录错误，完成平台登录后再进行真实正向验收。

## 容器的定义

- 一个电商容器归属一个平台中的一个店铺账号，显示名称使用店铺名。平台是账号所属信息，店铺账号是会话隔离边界；同平台多个店铺可以同时存在。
- 同一家淘宝店的千牛、生意参谋、万相台共用同一个店铺容器，作为淘宝平台下的多个服务入口。各服务按实际需要分别核验登录与授权；需要补充登录或授权时，在该店原容器内完成。
- 跨平台经营的同名店铺分别建立容器，以平台图标或平台名称辅助区分。CLI 始终用稳定 containerId 定位；名称重复时要求选择具体 ID。
- 原生容器 ID 与存储分区保持对应。修改显示名称不改变会话归属；平台及店铺绑定变更须检查影响，避免在既有会话上静默改成另一个账号。
- 浏览入口在同一个 Ecom 窗口内打开相应容器标签。允许用户正常使用浏览器窗口能力；产品不为每个店铺创建独立浏览器实例或调试端口。
- 继续使用同一容器承载登录跳转、弹窗和关联认证域。平台归属是产品与身份校验信息，不自动成为网站导航的域名封锁规则。

## 创建流程

1. **选择平台**：显示已实现的平台入口及验证能力；平台选择决定登录起点和身份读取适配器。仅有入口但尚不能核验的平台明确显示能力缺口。
2. **填写店铺名称**：必填；可选择容器颜色。后台先创建带稳定 ID 的待配置会话，以便在该会话里登录；此时产品上的添加尚未完成。
3. **进入登录**：在同一 Ecom 中打开明确标识该店铺的容器标签，用户在平台官方网页完成登录及验证码。平台凭证由浏览器原生会话管理。
4. **核验身份**：通过该平台已验证的只读能力检查实际登录、稳定店铺/账号 ID 与平台返回的店铺名。向用户展示识别结果及与填写名称的差异；不以用户点击“已登录”、Cookie 存在或接口 HTTP 200 代替平台核验。
5. **完成添加**：记录核验来源、时间和身份，将容器标记为可用。暂不具备验证能力时，保持待验证并说明具体缺口。

用户可在待配置状态继续登录。取消向导后，已产生会话的数据处理须明确提示；保留待配置记录是默认恢复方式，删除数据遵循项目已有确认规则。

## 核心信息

| 信息 | 用途 |
| --- | --- |
| containerId | 既有原生稳定 ID，GUI/CLI 共同定位 |
| platformId | 来自受控平台目录，定义入口与验证适配器 |
| name | 用户识别的店铺名称 |
| color / icon | 延续原生标识，平台和店铺视觉区分 |
| shopId / accountId | 从平台核实的稳定身份，具体字段按平台合同定义 |
| authenticationState | 待登录、待验证、可用、登录失效、身份不符 |
| verification | 来源、核验时间、实际返回名称、证据级别 |

状态必须来自实际证据：历史登录成功不保证永久有效；离线时保留上次核验时间，不能显示为刚刚核验。遇到账号切换、登录失效、权限或风控错误，停止对应业务操作并给出同容器恢复入口。身份不符不能通过自动改绑掩盖。

同店主账号、子账号及同名多店的具体展示策略，需在对应真实场景出现时补充；名称不能作为唯一身份键。

## 界面

- 独立管理页 `ecom://shops/` 使用平台分类侧栏和账号列表，提供搜索、状态筛选、添加店铺、服务选择、登录与身份核验。工具栏的网格按钮和容器菜单可直接打开管理页，设置保留外观选项与管理链接。
- 容器入口沿用地址栏附近的原生容器选择体验。选择项显示平台、店铺名称和状态；当前标签持续显示店铺与颜色标识。
- 店铺列表按平台分类，提供搜索、状态筛选、添加店铺、打开平台、编辑名称／原生图标／主题色、删除及登录检查。未指定平台的既有账号在“全部账号”中显示“平台待设置”，保持原有会话。
- 删除先返回带五分钟有效确认 ID 的预览，列明目标及打开标签数量；关闭目标容器标签后才能确认删除。网站数据按原生容器机制清理，历史恢复引用可能推迟物理清理。
- 点击已配置店铺后，在目标容器打开其平台入口。后续新标签、弹窗、认证跳转维持原生容器归属。
- 现有三个容器保持 ID、名称和会话。新功能上线时按明确操作补充平台与身份信息；普通/买家容器与店铺容器明确区分，不强制把全部原生容器转成商家账号。

## CLI 与职责

Ecom 原生能力管理容器生命周期、平台信息、可见登录入口和身份绑定；平台适配器提供固定、只读的登录及身份核验合同；sycmcli 等业务 CLI 负责注册业务接口和参数；应用 Skill 负责业务判断。

GUI 和 CLI 复用相同能力与校验。macOS Dev 原生命令为 `shops manage|platforms|list|refresh|create|configure|open|verify|confirm|update|delete-preview|delete`，分别覆盖管理页、平台目录、店铺列表、创建、配置已有容器、服务入口、身份核验和确认绑定。原有 `containers list` 与 `session get` 继续提供会话与取数通路。完整 schema、doctor 和 Windows 原生传输仍是能力缺口。

取数固定 containerId，并检查平台与已绑定身份；失败时报告登录失效、身份不符或平台验证能力缺口。普通取数复用原生网络服务，保持当前无 CDP 的正常启动约束。

## 最小实施顺序与验收

macOS 独立管理页的构建、界面与容器归属测试见 [2026-11-02 验收记录](shop-manager-test-2026-11-02.md)。平台身份核验的未完成项在该记录中单列。

1. 平台目录提供淘宝／天猫、抖音、拼多多、京东、小红书与自定义平台。淘宝保留千牛、生意参谋、万相台入口；其他内置平台使用商家官网入口，自定义平台填写名称和 HTTPS 登录网址。自动登录核验逐平台接入并标明能力。
2. 增加与原生容器 ID 关联的平台和状态信息，不改变已有存储分区或复制 Cookie。实现创建向导、同容器人工登录入口及对应 CLI。
3. 补齐平台身份验证与绑定，验证待登录不能完成、正确店铺成功、身份不符停止、会话失效后可恢复。
4. 保留双店交替与同时取数、页面关闭后后台取数及正常浏览体验验收。身份验证不能引入调试端口或切换其他店铺会话。

## 自动登录检查与有效期

原生服务每 60 秒安排已接入平台的后台检查，自动并发上限为两个，重复自动检查至少间隔 30 秒。管理页在打开／返回时请求检查，每五秒读取检查结果；用户编辑、删除或选择服务时保留当前交互。刷新按钮可显式请求重新检查。

淘宝当前通过生意参谋的固定只读接口检查服务登录。业务码与已知响应结构确认成功后显示“已登录 · 登录已核验”；登录错误显示该服务需登录，网络或格式不明时保留待确认。该登录证据不等于已识别具体店铺，不自动绕过店铺身份绑定；名称相符的真实店铺身份或用户确认的候选身份才进入身份已绑定状态。其他平台当前只提供独立容器及登录入口，显示“自动登录核验待接入”。

登录状态显示最近检查时间。原生 Cookie 管理器仅提供选定淘宝认证 Cookie 的期限元数据供参考，Cookie 值留在浏览器内。会话 Cookie、持久 Cookie 参考到期日与网站实际登录有效期分别表达；准确平台期限未公开时显示由平台决定。服务端撤销、风控或单独服务授权以实际响应为准。

## 跨服务验收

同店的千牛、生意参谋、万相台标签与后台请求应映射到同一个稳定 containerId；同平台不同店铺及跨平台账号分别映射到各自容器。逐项验证服务入口、跨域认证跳转、实际店铺身份、授权状态与会话恢复。某一服务核验成功后，其他服务的状态仍以各自实际检查结果为准。

## 调研依据与证据边界

2026-11-02 查看用户提供截图及本机运行中的挖象管理中心，观察到：账号列表分别展示名称、平台/账号；添加表单包含必填“所属平台”“名称”，以及登录账号、登录密码、绑定设备等字段；平台目录区分千牛、生意参谋、1688、拼多多等入口。调研只查看表单及平台下拉，随后返回原账号列表，没有新增账号、提交凭证或更改账号配置。

尚未提交其创建流程，不能据此断言挖象会强制登录核验或采用何种会话实现。Ecom 的创建时登录要求来自本项目用户需求；底层采用现有原生容器隔离。挖象的账号管理方式仅作为产品交互参考，未据此扩展 Ecom 的浏览器环境或设备模拟范围。
