# Ecom 内存管理现状与优化方案

调研日期：2026-11-06，Asia/Shanghai。范围：当前 Mac 上正在运行的 Ecom Dev、Google Chrome、Brave，以及 GitHub 上的浏览器源码与设计资料。本次交付为测量与方案，浏览器行为、用户标签页及配置保持原状。

## 1. 结论与建议

**优先建设“保留账号会话、按需保留网页运行状态”的内存管理，而不是重写浏览器引擎。** 用户可以保留大量标签和多个店铺账号，但只有正在使用、近期可能切回及有持续业务职责的页面需要长期驻留。

1. **Ecom 当前并非主进程过大。** 约一分钟、5 次测量中，整个实例的内存 footprint 中位数为 **1.84 GiB**；代表样本中网页渲染进程占 **73.6%**，GPU 占 **14.6%**，主进程占 **7.4%**。先优化网页生命周期，预期收益大于只裁剪菜单或设置界面。
2. **现有内核已有主要机制，产品策略与可观测性需要补齐。** 本地源码包含冻结、定时卸载、卸载资格检查与压力回收路径；Local State 中没有显式保存 Memory Saver 状态，注册默认值为关闭。由此推测当前采用关闭默认值，但有效运行时配置尚需原生接口核验。基线的定时卸载档位为 **6／4／2 小时**，不适合作为电商重页面唯一的回收依据。
3. **当前对照不能证明 Ecom 比 Chrome 或 Brave 更省内存。** 三者的页面、扩展、运行时长及会话不同，Chrome 还开着三个独立实例。此次得到的是用户真实桌面的现状；性能优劣需要同条件复测。
4. **推荐实施顺序：原生观测 → 安全卸载 → 按需恢复 → 容器与后台服务优化 → 缓存和分配器专项。** 以多标签下总 footprint、恢复速度和业务安全一起验收。

## 2. 实测现状

### 2.1 条件与口径

设备为 Mac16,7，24 GiB 内存，14 个逻辑 CPU，macOS 26.5.2（25F84）。正式采样时间为 **11:19:05—11:20:05**，间隔约 15 秒，共 5 次，跨度 60.69 秒。浏览器继续运行原有工作负载；本次没有重启、强制 GC、清缓存、卸载页面或连接调试入口。

采集通过 macOS `proc_pid_rusage(RUSAGE_INFO_V0)`，按主进程 PID 和父子关系归组，涵盖主进程、renderer、GPU 与 utility。所有纳入进程的查询均成功。与主进程脱离父子关系的 crashpad handler 未纳入，因此不是整套安装的穷尽统计。采样是逐进程读取，非原子快照。

- **Footprint**：macOS 对进程的内存记账负担，包含压缩内存等项目，作为本报告主要比较指标。它不是当前占用物理 RAM 的简单大小，也不是网页 JS 堆大小。
- **Resident／RSS**：当前驻留内存，容易受压缩、换出及共享页影响。相加不能当作系统唯一物理内存占用；在高压缩环境下，单看 RSS 尤其容易低估仍然保留的网页状态。
- 表中 MiB 为 2²⁰ 字节，GiB 为 2³⁰ 字节；中位数按实例每次总量计算。进程数不是标签页数。
- GPU 与共享资源的跨进程记账可能交叠，实例 footprint 加总用于同口径趋势判断，不等于全系统去重后的物理占用。

原始测量与方法见 [measurements.json](memory-research-2026-11-06/measurements.json)、[summary.json](memory-research-2026-11-06/summary.json)、[context.json](memory-research-2026-11-06/context.json) 和 [采样脚本](memory-research-2026-11-06/sample-processes.py)。记录包含 PID、进程类别和指标，不保存页面 URL、Cookie、完整启动命令或店铺身份。

以下为 11:19:35 的同一代表样本，总量 1910.6 MiB；此表不是各分组的中位数。

| 类别 | 数量 | Footprint | 占实例比例 | 判断 |

最大的 renderer 分别约 365.0、284.4、227.7、195.3、194.3 MiB，前五个合计约 **1266.7 MiB**。这些 PID 尚未和页面、iframe、worker 建立原生映射，不能直接指认某个网站泄漏。当前活动页的标签可访问性文字曾显示“小红书搜索，内存用量 342 MB”；这是浏览器自己的页面指标，与 OS footprint 口径不同，也不足以将其与某个 PID 一一对应。

这 60 秒内，最大 renderer 的平均 CPU 约为单核的 0.67%，GPU 约 0.06%。**页面不忙仍可保留大量内存**，仅降低后台 CPU 或冻结定时器，未必能释放已持有的 DOM、JS 堆和图像。一分钟波动不能用于诊断内存泄漏，需要更长时间及重复操作的回收曲线。

### 2.4 系统状态

正式采样中，交换空间使用由 9718.19 MiB 降至 9686.19 MiB，压缩器物理占用约为 **7.97—8.05 GiB**。同期 swapout 计数没有增加，swapin 增加 2171 页，约 33.9 MiB；计数为全系统值。

这说明系统经历并保留着明显的压缩／交换负担，**不能仅凭已有 swap 数量断言此刻发生严重抖动，更不能全部归因于浏览器**。采样后 `memory_pressure -Q` 报告 free percentage 为 43%，与 `vm_stat` 空闲页比例并非同一指标。本次未记录连续的原生压力等级事件；后续验收需同时采集压力、换页速率和交互延迟。

## 3. 源码与 GitHub 调研

### 3.1 理论：把网页作为可回收工作集

标签是用户的工作目录；正在执行的网页才是昂贵的运行状态。浏览器需要同时管理活跃工作集、恢复成本、可回收收益及用户任务安全。

**进程隔离有成本，也承担安全和稳定性。** Chromium 的进程模型明确将并行、崩溃隔离、安全与内存开销作为取舍；不同 StoragePartition 的文档不能共享同一 renderer。因此，Ecom 多店铺隔离本身会产生合理开销。优化应保留站点与容器边界，在同一边界内复用机制并减少不必要的常驻页面。[Chromium 进程模型与站点隔离](https://github.com/chromium/chromium/blob/main/docs/process_model_and_site_isolation.md)

**观测、策略、执行应分开。** Chromium Performance Manager 用 Page／Frame／Process／Worker 图表达资源关系，由策略选择回收对象，再由机制执行。Ecom 应在这一共同能力层补充容器、任务保护及观测，不另建一套与内核竞争的进程管理器。[Performance Manager 设计](https://github.com/chromium/chromium/blob/main/components/performance_manager/README.md)

### 3.2 开源实现比较

| 项目／来源 | 已核实的机制或边界 | Ecom 采用方式 |
| --- | --- | --- |
| Chromium | Memory Saver 按不可见时间及重访情况安排卸载；资格策略检查页面与活动状态 | 复用原生卸载和资格检查，调整产品档位及压力策略 |
| Brave | 本地及 GitHub 覆盖文件停用部分 UMA／UKM 资源监测；不等于停用整个 Performance Manager | 保留低开销本地诊断，避免把监测缺失当作功能缺失 |
| Firefox | TabUnloader 综合最近使用、媒体／WebRTC 等保护状态、进程共享与资源估算排序 | 借鉴“预计真正可回收的资源”，避免只按标签年龄排序 |
| Qt WebEngine | 提供 Active／Frozen／Discarded 及 recommendedState 接口 | 借鉴清晰可解释的状态模型；Ecom 仍使用自身 Chromium 原生路径 |
| Ladybird | 采用 UI、WebContent、图像解码、网络等多进程架构；README 标示开发阶段 | 作为架构参照，未获得其更省内存的同条件证据，不建议为此更换引擎 |

对应源码：[Chromium Memory Saver](https://github.com/chromium/chromium/blob/main/chrome/browser/performance_manager/policies/memory_saver_mode_policy.cc)、[卸载资格](https://github.com/chromium/chromium/blob/main/chrome/browser/performance_manager/policies/discard_eligibility_policy.cc)、[Brave 资源监测覆盖](https://github.com/brave/brave-core/blob/master/chromium_src/chrome/browser/performance_manager/chrome_browser_main_extra_parts_performance_manager.cc)、[Firefox TabUnloader](https://github.com/mozilla-firefox/firefox/blob/main/browser/components/tabbrowser/TabUnloader.sys.mjs)、[Qt 状态接口](https://github.com/qt/qtwebengine/blob/dev/src/core/api/qwebenginepage.h)、[Ladybird README](https://github.com/LadybirdBrowser/ladybird)。

这些链接是调研当日读取的动态分支，不构成 Ecom 基线升级建议。实施以本地固定 Chromium 156.0.8078.80 的接口和测试为准。当前根仓库提交为 `180518772f010e2e103f9c9c8802d69ec3efdc22`，构建工作树 HEAD 为 `61456ca4a68d421a17f9bb0a0af709e5d4771b69`；尚未把运行二进制绑定到精确源码提交。因此源码结论是候选解释，运行行为应通过原生诊断再次确认。关键本地文件哈希已保存在 context.json。

### 3.3 本地代码的重要发现

1. `chromium_src/chrome/browser/performance_manager/chrome_browser_main_extra_parts_performance_manager.cc` 只替换部分监测组件。Chromium 主实现仍注册冻结、Memory Saver 和卸载资格等机制；压力回收路径存在平台宏及 feature 条件，macOS 与 Windows 必须分别核对。
2. `components/performance_manager/user_tuning/prefs.cc` 在本地 Chromium 中将 Memory Saver state 注册为 disabled，冻结开关注册为 true。**开关默认值与所有页面已冻结是不同事实**；资格、feature 和运行活动仍决定执行情况。
3. `memory_saver_mode_policy.cc` 的档位为 6／4／2 小时，还按重访次数避免卸载。需要从正在运行的 PrefService／策略读取有效值；配置文件缺项只能结合默认值做推断。
4. `browser/ecom/shop_container_service.cc` 每 60 秒触发检查调度，自动核验并发上限为 2。`native_session_service.cc` 已对读取任务设并发上限 2，普通响应上限 2 MiB，并在完成后移除请求；业务读取也有响应边界。**不是无界并发取数**，下一步应测量多容器闲置开销和重复初始化，而非假设此处已泄漏。
5. 源码的部分卸载 reason 可以越过常规保护检查。Ecom 的手动、自动和 CLI 卸载都应先执行统一保护校验，避免以外部调用路径绕过业务安全规则。

## 4. 目标设计

### 4.1 责任划分与最小缺口

Chromium 负责分配器、V8／Blink GC、站点隔离、网页生命周期及底层回收。Ecom 原生能力层负责稳定标签／容器身份、资源归属、策略、任务保护及恢复。GUI 与 `@petercjl/ecom-cli` 调用同一能力；CLI 负责发现、验证、结果与恢复契约。电商 Skill 负责判断业务任务、是否需要页面及何时申请任务保护。

**最小新增能力是只读资源快照**：返回当前实例的有效内存策略、进程分类、窗口与标签、容器归属、可卸载状态及受保护原因。先形成可验证归因，再更改回收行为。

### 4.2 标签生命周期

| 状态 | 行为 | 用户体验 |
| --- | --- | --- |
| 活动 | 正常加载与执行；保留近期常用工作集 | 切换与交互优先 |
| 后台 | 使用原生后台调度，重新评估持续任务 | 标签保留，可快速切回 |
| 冻结 | 暂停可冻结页面的执行，通常仍保留大部分堆 | 快速恢复；主要限制后台活动 |
| 已卸载 | 释放可释放的页面运行状态，保留标签导航与容器归属 | 显示休眠标记，点击后重新加载 |
| 按需恢复 | 重启时先恢复标签元数据，选中后加载 | 避免启动时同时唤醒全部重页面 |

状态是逻辑模型，不要求所有页面按顺序经过每一状态；紧急情况可直接从合格后台状态卸载。共享进程／worker 会影响实际回收，卸载一页不保证对应进程立即退出。

**保留持久 Cookie／LocalStorage 等与保留网页内存分开处理。** 卸载不清理账号存储，不改变容器 ID；重新加载后网站仍可能因过期、平台校验或页面内存态丢失要求重登。SessionStorage、滚动位置和表单恢复以原生能力和逐项测试为准，不承诺完整快照网页运行状态。

### 4.3 默认策略与待验证参数

建议提供“保守／平衡／节省”三个档位，默认先灰度平衡档；已有用户配置显式保留。以下均为 **待验证的初始参数**，不是已实现行为或性能承诺。

| 档位 | 合格后台页最短闲置时间 | 平常行为 |
| --- | --- | --- |
| 保守 | 60 分钟 | 原生冻结与压力回收优先 |
| 平衡 | 30 分钟 | 结合内存预算，优先卸载长期闲置重页面 |
| 节省 | 10 分钟 | 缩小近期工作集，更积极回收可恢复页面 |

时间是候选条件，不是到时无条件执行。根据系统压力、实例 footprint、近期切回和业务保护共同决定。首轮在 24 GiB 本机试验 **3 GiB 软预算、2.5 GiB 回收停止点**，与原生压力事件并行；它们只是触发和停止阈值，不是硬内存上限。跨 8／16／24／32 GiB 设备校准后再决定默认值。受保护页面超过预算时明确显示原因，不强制终止。

调度一次卸载一页，异步完成后观察约 5—10 秒，依据实际变化决定是否继续；同一实例只有一个回收协调器。压力缓解有滞回，防止反复回收。被用户唤醒的页面至少保护 10 分钟；这是附加保护，不替代更长的档位闲置条件。恢复页不主动连带唤醒同店铺的其他页面。

### 4.4 业务保护与任务租约

自动冻结与卸载共用安全判定，但保留各自差异。所有可见窗口的可见标签、近期交互、音视频／会议、屏幕共享、上传、未提交表单、登录／验证码流程和显式保持活动的页面均需要保护。持续客服、站内通知和长连接工作台提供用户可见的保持活动入口；识别不充分时采用保守保护，不仅凭静音或后台时间推断可卸载。

Agent 页面任务在 `instanceId + containerId + tabId + pageVersion` 上申请限时保护，完成释放、超时到期；观察到任务仍在执行时续约。页面保护遵循真实依赖：纯原生 JSON 请求保护目标容器请求上下文，不应因此锁住该容器所有网页。基于页面的签名／认证初始化则保护实际依赖页。

网页下载已交给浏览器下载服务时，页面能否卸载需单独验证；上传和页面依赖下载继续保护。保护规则的紧急降级属于独立设计项，首版不以紧急原因绕过业务硬保护。

### 4.5 容器与后台请求

1. **账号常驻，页面按需运行。** 读取任务优先复用指定 StoragePartition 的原生网络上下文；适配器无需 DOM 时，业务页休眠仍能取数。若需要补充认证或页面初始化，返回明确状态，在原容器准备，保持前台焦点。
2. **保持后台请求有界。** 复用已有并发和响应限制，补充所有读取与自动核验之间的总调度、超时取消和任务完成释放；基于实测限制重复 JSON／字符串拷贝及结果缓存。不能把响应上限直接当成整个流程峰值内存。
3. **闲置店铺分级检查。** 候选方案为活跃店铺维持必要检查、无任务且无打开页的账号逐渐退避至 5—15 分钟；用户主动检查立即执行。显示最后核验时间，状态新鲜度和资源开销一起验收。
4. **先测量再管理分区驻留。** 验证 0／2／10 个容器中 NetworkContext、缓存、Service Worker 的增量成本。仅在 Chromium 支持且无在途任务时释放可重建对象；不手工销毁仍被使用的分区，不清理账号数据，也不合并不同容器的 renderer。

## 5. GUI 与 CLI 交付契约

以下均为拟新增能力，当前 CLI 尚未实现。实施时需加载包开发及 portable Skill 流程，更新 canonical Skill、capabilities、schema、帮助、测试与迁移台账。

| 拟议 CLI | GUI 对应 | 核心契约 |
| --- | --- | --- |
| `memory status --json` | 性能页概览 | 实例、版本、有效策略、压力、总量、指标口径和采样时间 |
| `memory tabs --json` | 标签资源列表 | 窗口／标签／容器 ID、页面版本、状态、保护原因、内存估算质量 |
| `memory inspect --tab …` | 标签详情 | Page／Frame／Worker／Process 关系，返回不可归因及共享部分 |
| `memory policy get/set …` | 三档策略及例外 | 同一验证与偏好写入；支持恢复原值 |
| `tabs discard --tab … --expected-page-version …` | 右键休眠 | 复核保护与目标；返回实际是否执行及操作 ID |
| `tabs wake --tab …` | 点击恢复 | 默认后台恢复；激活前台为显式选项 |

通过现有私有认证通信扩展，不增加网页可调用的管理接口或调试端口。结果含协议版本、精确实例、操作 ID、超时、执行状态、可否重试、恢复方式。连接中断后先查询操作，避免重复唤醒或误操作新页面。指标不可得时返回 `unavailable`，不填 0；共享 renderer 的完整内存不得重复归给每个标签。低频观测、短期环形缓存与按需详细诊断，避免监测自身常驻消耗过大。

## 6. 实施阶段与验收

| 阶段 | 主要交付 | 必须通过的退出条件 |
| --- | --- | --- |
| P0：可观测性 | 原生只读资源快照、有效配置、映射与基线 | 核对 OS 总量及口径差异；同一进程不重复累计；两容器归属正确；不影响焦点 |
| P1：安全回收 | 平衡档、保持活动、统一保护和按页卸载 | 本地夹具覆盖表单、媒体、上传、任务冲突；两个持久容器休眠／唤醒无串号 |
| P2：按需恢复 | 延迟加载、受控恢复队列、后台取数解耦 | 30／100 标签重启不同时加载；容器归属、业务响应及真实店铺身份逐项核验 |
| P3：多容器与基础开销 | 核验退避、分区驻留诊断、未使用功能审计 | 10 账号静置与循环取数曲线趋稳；真实服务状态与资源收益都有证据 |
| P4：专项优化 | GPU／图像、缓存、BFCache、预渲染、分配器 | 每项独立 A/B；保留响应性、返回速度及安全边界 |

P0 先让 Ecom 对自己的资源与决策给出可信解释。P1 只落地当前任务需要的最小策略，不把所有长期 CLI 功能作为前置。源码修改沿项目统一流程提交、集成 main、串行增量构建并通过 `node ecom/build-dev.mjs` 验证；本轮方案不触发编译、重启或发布。

### 6.1 测试矩阵

| 维度 | 场景与测量 |
| --- | --- |
| 标签规模 | 1、10、30、100 标签；记录已加载／冻结／卸载数和 1／5／30 分钟曲线 |
| 容器规模 | 1／2／10 容器，相同站点与跨站点组合；区分空容器和已初始化分区 |
| 工作负载 | 本地静态页、可控 JS／图像页、真实电商后台、商品／搜索、客服与上传 |
| 安全与恢复 | 表单、SessionStorage、跨域登录、弹窗、过期、验证码、崩溃、正常重启 |
| 并发 | 用户切换标签、Agent 固定目标、同页导航、回收／唤醒并发及请求取消 |
| 长时间 | 2 小时静置、8 小时真实使用、打开关闭 100 轮；记录稳定区间与增长斜率 |
| 平台 | macOS 先验收；Windows 在 peter-new 独立核对压力信号、Private Bytes／Working Set 与恢复 |

Chrome／Brave 对照使用相同机器、同一页面清单、相同登录与扩展条件、相同恢复和缓存状态、相同等待时点，并记录各自 Memory Saver 档位与内核版本。浏览器测试顺序轮换，每条件至少 3 轮；尽量串行，控制其他应用负载。OS 压缩与交换历史作为协变量记录，测试过程中不破坏既有会话。macOS 组件版与发布配置分别比较，正式版测试使用项目规定的独立临时数据目录。

### 6.2 初步目标

下列为工程目标，**尚无本轮 A/B 数据证明可以达到**：

1. 在 30 标签、2 个容器、后台合格页面占多数的可控场景，平衡档稳态实例 footprint 比 Ecom 关闭主动节省策略降低 **至少 30%**；另报所有受保护页占多数的场景，不能挑选有利结果替代真实业务。
2. 在已确认可卸载的相同页面集合上，达到 Chrome／Brave 同等或更低的稳态 footprint，再评价恢复成本。100 标签主要验证曲线与容量，不预设每页固定内存。
3. 现存未卸载页的切换 p95 相对基线劣化不超过 10%；卸载页在本地受控夹具的交互就绪 p95 目标不超过 2 秒。真实站点分别记录网络与认证耗时，不将其算作已达标。
4. 所有业务安全必测场景均通过：零跨容器会话串用、零自动丢弃已知未提交编辑、零重复提交、零后台取数抢占前台。长期内存是否泄漏通过重复操作后仍存活对象与回收曲线确认。
5. 诊断开销单独量测：稳态低频观测以平均单核 CPU 小于 1%、新增常驻 footprint 小于 20 MiB 为首轮预算；超预算则降低频率或改成按需。

## 7. 优化边界、回滚与后续诊断

保留沙箱、站点隔离、容器隔离及安全分配器保护；不以单进程、强杀 renderer、降低 V8 堆上限、周期清空系统工作集或清理登录数据作为默认方案。缓存和 BFCache 能换取速度，关闭必须有独立证据。图片资源阻断或网页内容删减属于改变业务体验的功能，需单独设计与评估。

每个策略有独立开关和版本记录，可恢复原偏好；回滚停止新回收，已卸载页面在用户访问时重新加载。回滚不能恢复已经丢失的页面内存态，因此保护判定须先于执行。出现恢复失败率升高、频繁再次加载或业务任务被打断时，自动停止新增主动卸载并保留本地诊断。

如果 P1／P2 后总量仍高，再通过浏览器原生任务管理与 MemoryInfra 定位 V8、Blink、PartitionAlloc、Skia、GPU、网络缓存和 worker。诊断使用内置原生入口／受控 CLI，保持普通有界面模式；详细采集按需进行，保存期限和脱敏单独处理。[Chromium MemoryInfra](https://github.com/chromium/chromium/blob/main/docs/memory-infra/README.md)

**建议下一项开发：完成 P0，只读回答“哪几个页面占内存、为何仍然驻留、可以安全释放多少”，随后用同一批页面验证 P1。** 这样每轮优化都有基线、业务保护与可审查收益。
